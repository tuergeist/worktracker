## Pläne: empty-save guard, content clarity, trend charts

Continuation of the Pläne feedback loop from 2026-08-18 (still all local, not yet committed/pushed — see that diary for the full history of the feature and the earlier rounds of UI correction).

### Changes Made

**Content fixes** (`frontend/js/plans.js`):
- Range's "Wind / Platz heute" moved from block 2 (Teildistanzen) to block 1 (Aufwärmen) — mirrors the earlier "Grün heute" placement decision for Kurzspiel (asked once at the start, not mid-flow).
- "Teildistanzen · 50 m" block was confusing on two counts, both raised by the user from real usage: the description mentioned practicing at 8/9/10 Uhr swing lengths but only asked for the 9 Uhr value (now explicit: "8 und 10 Uhr dienen als Kalibrierpunkte drumherum"), and "Auf 50 m ±5 m" never explained what the number meant (now: "10 Bälle aufs 50-m-Ziel — wie viele landen im Fenster 45–55 m?", field label renamed to "Treffer im Fenster 45–55 m").

**Empty-run guard**: `saveRun()` now checks `hasAnyData()` before posting — if every field is still at its untouched default (null/empty/0), it blocks the save (haptic warning + `alert()`) instead of writing a blank history card. Triggered by a real example: a fully-empty Range run on the live site with nothing but a date. Note the inherent tradeoff: count/greenScale fields use `0` as their "unselected" sentinel, so a run where every recorded value is genuinely 0 also gets blocked — accepted as correct behavior since an all-zero accidental-tap run and an all-zero intentional-report run are indistinguishable from stored state alone, and the former is far more common.

**Trend charts** (new, scoped via two AskUserQuestion rounds with the user): Statistik → Pläne now has a metric chip row (reuses `.club-strip`/`.club-row`/`.club-chip` — same "pick one, see its trend" pattern Range already uses for clubs) above the history-card list, showing one `lineChart()` (existing `chart.js`, zero new charting code) for whichever numeric field is selected. Scoped to genuine distance/count fields only (`chartableFields()` filters to types `number`/`count`/`gap`) — excludes the green-speed scale, free text, and notes. `local.plansRuns` caches the last fetch so switching the selected metric re-renders instantly without a network round-trip. `index.html` gained `#plans-metric-row` + `#plans-chart` in the Pläne stats pane.

Empty-save guard tested both ways: blank step 7 → blocked, stays on step 7, no confirmation screen; same step with one field filled → saves normally. No console errors throughout. All test/backdated runs deleted afterward.

Committed (`fix(plans): app-shell scroll bug, touch targets, trend charts`) and pushed — deploy confirmed via GH Actions run `32224838397` (success).

## False alarm: "delete/date-edit does nothing" in Pläne Verlauf

User reported tapping date/time and ✕ in the history cards did nothing. Investigated at length: the wiring (`hist.querySelectorAll("[data-del]"/"[data-edit]")` + `.onclick=`) is structurally identical to Putten's pre-existing, unmodified session delete/edit-date flow. Clicking Putten's delete button via browser automation showed the *same* "nothing happens" symptom — strong evidence the test tooling here silently swallows native `confirm()`/`showPicker()` dialogs, not a real code bug. Asked the user to compare against Putten's delete on their actual phone: **works fine on-device for both** — confirms it was a deploy-rollout timing issue (they tested mid-rollout), not a bug. No code change made. Worth remembering: this environment's browser automation cannot be used to verify anything gated behind `confirm()`/`alert()`/`showPicker()` — a "does nothing" result there is inconclusive, not a finding.

## UI/UX-Review aus Sicht eines 40–50-jährigen Clubgolfers, und die Umsetzung daraus

Nutzer bat um ein Review der App aus der Perspektive der eigentlichen Zielgruppe. Da kein lauffähiges Backend da war (kein venv, `asyncpg` nicht installiert), habe ich einen stdlib-Mock-Server im Scratchpad gebaut, der `frontend/` statisch ausliefert und die API-Endpunkte mit Beispieldaten beantwortet. Damit ließ sich die App komplett durchklicken und begutachten.

**Zwei Fallen bei dieser Methode, die Zeit gekostet haben und beim nächsten Mal sofort zu prüfen sind:**

1. Firefox hat die ES-Module nach einer Änderung weiter aus dem HTTP-Cache bedient. Der Mock-Server schickte anfangs keinen `Cache-Control`-Header, nur `Last-Modified` — damit greift heuristisches Caching, und im DevTools-Netzwerkpanel sehen die Requests aus wie echte 200er, obwohl sie aus dem Cache kommen (erkennbar am eingefrorenen `date`-Header und der alten `content-length`). Nachträglich `no-store` zu senden reichte nicht; die Einträge waren schon als frisch markiert. Gelöst durch **Portwechsel** (8123 → 8124), was den Cache-Key der Origin ändert. Die echte App hat dafür bereits eine Middleware.
2. Der Fehler war ein `TypeError` in einer `async`-Funktion, also eine *unhandled rejection*, kein `window.onerror`-Ereignis. Ein `window.addEventListener("error", …)` fing nichts. Erst `unhandledrejection` lieferte den Stack. Merken: `main.js` ruft alles aus einer async IIFE auf, Init-Fehler tauchen dort nie als Fenster-Fehler auf.

### Befunde, die wirklich zählten

Kern des Reviews war nicht die Optik, sondern dass die App an drei Stellen still Daten verdirbt oder verliert:

- **`wireCount` setzte jedes Zählfeld beim Aufbau auf 0** und schickte es mit. Wer im Kurzspielplan einen Block auslässt (bei 50 Minuten Laufzeit normal), speicherte „0/12" als echtes Ergebnis — und `renderChart` filtert nur `null`, also landete die 0 in der Trendkurve. Gleichzeitig war eine echte 0 gar nicht erfassbar, weil der Picker bei 1 anfing. Beides gelöst, indem 0 ein auswählbarer Wert wurde und „nichts ausgewählt" nun `null` bedeutet.
- **`wirePlanSegButtons` band `document.querySelectorAll(".seg-control__btn[data-key]")`** — also *auch* die beiden Knöpfe im Statistik-Tab. Wer mitten im Durchlauf in die Statistik ging und dort den Plan wechselte, löste `selectPlan()` aus und damit `local.data = {}`. Aufnahme und Statistik haben jetzt getrennte Auswahlen (`local.planKey` / `local.statsPlanKey`), gescoped über `#view-plans` bzw. `#stats-pane-plaene`.
- **Kein `catch` um irgendeinen schreibenden Aufruf.** Auf der Driving Range mit schlechtem Empfang passierte beim Tippen auf Speichern sichtbar gar nichts. Neu: `withSaveFeedback()` in `ui.js` plus ein Toast. Bewusst so gebaut, dass die Eingabe bei Fehlschlag *stehen bleibt*, statt zurückgesetzt zu werden.

Dazu kam ein Bug mit ähnlicher Ursache wie der Segment-Bug: `putting.js` `goStep()` selektierte `.step-dot` global statt im eigenen Container und verstellte damit die Schrittanzeige der Pläne. Erledigte sich, weil die Putten-Schritte ganz entfielen.

### Foto-Feature raus, Putten auf eine Seite

Nutzer entschied nach eigenem Test: das Green-Foto kann komplett weg. Damit fiel auch die Begründung für den Drei-Schritt-Ablauf, denn die Schritte existierten nur, um Spielen/Foto/Zählen zu trennen. Zähler liegt jetzt direkt auf der Aufnahmeseite.

Wichtige Korrektur an meinem eigenen Vorschlag: ich hatte „nach jedem Ball einzeln tippen" empfohlen. Der Nutzer hatte das real ausprobiert und für unpraktisch befunden — gefehlt hat ihm ein **Rest-Button**: zwei 2-Putts tippen, dann in der 1-Putt-Zelle „Rest +8". Das ist die Bewegung, die tatsächlich passiert. Umgesetzt mit `visibility:hidden` statt Ausblenden, damit sich beim letzten Ball nichts unter dem Daumen verschiebt.

Backend-seitig sind mitentfernt: `/api/analyze-putt`, der `sys.path`-Hack auf `tools/putt-analyzer`, `numpy`/`scipy`/`pillow` aus `requirements.txt`, `ANTHROPIC_API_KEY` aus Compose und k8s, die `proxy-body-size: 16m`-Annotation im Ingress-Beispiel. `tools/putt-analyzer/` selbst bleibt als eigenständiges Tool mit eigener `requirements.txt`.

Nebenbei fiel auf, dass das Backend nie eine feste Ballanzahl verlangt hat — die Sperre „nur exakt 10/10 speicherbar" war reine Frontend-Blockade. Teilsessions sind jetzt speicherbar.

### Lesbarkeit: gemessen, nicht geschätzt

`--text-muted` (#6b766b) lag auf dem App-Hintergrund bei **4,37:1**, also unter WCAG AA — und genau dort steht der Großteil der Sekundärtexte, inklusive der kompletten Übungsbeschreibungen der Pläne bei 17px. Neu #525d52 mit 6,35:1. Die Nullen im Zählraster standen in `--divider` bei **1,16:1**, praktisch unsichtbar; dafür gibt es jetzt `--text-faint` (2,99:1, gerade die Large-Text-Schwelle bei 3rem Schriftgröße).

Alle 72 px-Schriftgrößen sind auf rem umgestellt, damit die Text-/Zoom-Einstellung des Browsers überhaupt greift, und das kleine Ende ist angehoben (10→12, 11/12→13, 13→14, 14→15). Eine Ausnahme mit Kommentar: `.chart-tick` liegt in SVG-Nutzereinheiten, die von der viewBox nochmal um ~1,4 gestreckt werden — dort wäre rem doppelt skaliert worden.

`--touch-min: 48px` war definiert und wurde fast nirgends benutzt. Neues Token `--tap-min: 44px` als Untergrenze; die Lösch-✕ waren vorher ~24×28 direkt neben antippbaren Zeilen.

### Range-Distanzkörbe aus der eigenen Historie

`CLUB_CENTERS` war eine feste Tabelle mit Driver 200 m Carry — ein guter männlicher Mittdreißiger. Für einen 48-Jährigen liegt das systematisch zu hoch, der landet dauerhaft im untersten Korb. Dabei kennt die App über `avg_carry` längst die echten Werte.

Jetzt dreistufig, mit der Bucket-Breite als Vertrauensmaß: ab 3 Schlägen zentriert auf den eigenen Schnitt mit **10-m**-Körben (das ist der Punkt der Übung — Gapping), bekannter Schläger ohne Historie 20 m, selbst angelegter Schläger ohne Historie 30 m. Die Tabelle wurde zusätzlich auf realistische Mittelhandicap-Werte gesenkt und ist nur noch Startwert. Die Zusammenfassungszeile sagt jetzt, worauf die Bereiche beruhen („Bereiche aus deinen Schlägen" vs. „Bereiche sind Richtwerte") — ohne das wirken die Zahlen einfach falsch.

Zwei Fallen dabei: `local.stats` kommt asynchron, also musste `local.statsClubId` mitgeführt werden, sonst zentrieren die Körbe kurz auf den *vorherigen* Schläger. Und die Körbe werden nach dem Laden nur neu gebaut, wenn noch nichts ausgewählt ist — sonst würde eine bestehende Auswahl stillschweigend eine andere Distanz bedeuten.

### Diagramme hatten keine x-Achse

Das Datum steckte ausschließlich im SVG-`<title>`, also in einem Hover-Tooltip, den es auf dem Handy nicht gibt. Man sah eine Kurve und wusste nicht, über welchen Zeitraum. Jetzt maximal 4 Beschriftungen, gleichmäßig verteilt, erste und letzte immer dabei, die äußeren nach innen verankert damit sie nicht abschneiden. `padL` von 32 auf 44 — vorher lief „139.0 m" in die Achslinie hinein und die Minimum-Beschriftung wurde durchgestrichen.

Dazu ein `chart-hint` unter Diagrammen, deren Richtung nicht selbsterklärend ist: „weniger ist besser" bei Putts/Ball und bei den Anläufe-Feldern. Bei Range-Carry bewusst *nicht* — mehr Weite ist beim Golf nicht pauschal besser, da wäre die Aussage falsch.

Ebenfalls aus dem Review: die Felder `p1`/`p2` („Anläufe, bis alle 6 sitzen") wurden in der Historie als „2/6" dargestellt wie eine Trefferquote, obwohl weniger besser ist, und lagen im selben Chart wie Mehr-ist-besser-Werte. Jetzt „2 Anläufe" über ein `unit`-Feld, Zähler beginnt bei 1, `lowerIsBetter` steuert den Hinweis.

### Stand

Alles nur lokal, nichts committet. Im Browser über alle vier Ansichten geprüft, keine Konsolenfehler. Offen aus dem Review: kein Dunkelmodus/Kontrastoption für Sonnenlicht, keine PWA (kein Manifest, kein Service Worker — bei einer App, die man auf der Range öffnet), Abkürzungen „U&D/1 PL/2 PL/Mitte/Lag" unaufgelöst, „Abmelden" sieht aus wie „+ Schläger", Putten- und Statistik-Tabicon fast identisch (beide Zielscheibe), Statistik-Tab dupliziert die Taxonomie der unteren Leiste.
