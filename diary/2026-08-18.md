## Range-carry precision + login persistence

Two small follow-ups from the Pläne feature and general usage feedback.

### Changes Made

**Frontend:**
- `frontend/js/plans.js`: added `step: 5` to the Range plan's carry-distance fields (`i7`/`i5` in Wechselblock, `sw9`/`aw9` in Teildistanzen) and rendered it as the `step` attribute on the number inputs. Trigger: on a driving range you can only read carry off the distance markers to about 5m precision, so entering e.g. "128.5m" was fake precision. This matches the app's existing convention — `range.js`'s slider (`range-slider` in `index.html`) already uses `step="5"` for the same reason.

**Backend:**
- `backend/users.py`: session cookie + JWT lifetime was `86400` seconds (24h, both `cookie_max_age` and `JWTStrategy.lifetime_seconds`). User trains every 2-4 days and was getting logged out between sessions. Bumped both to `SESSION_LIFETIME_SECONDS = 90 * 24 * 60 * 60` (90 days) — this is a personal training log, not something that needs bank-grade session expiry.

## App Store packaging — decided NOT to do it now

Discussed wrapping scratchlab as a thin native shell (WebView pointed at `scratchlab.app`, no real native logic) to get an App Store/Play Store listing while keeping all logic server-side.

- Android: Trusted Web Activity is an officially supported Play Store app type — a bare web wrapper is fine there.
- iOS: Apple's App Store Review Guideline 4.2 ("Minimum Functionality") explicitly rejects pure web wrappers — needs at least one real native touchpoint (push notifications, Face ID lock, share extension, widget, etc.) to pass review. Also likely triggers Guideline 4.8 ("Sign in with Apple" required as an alternative once Google Sign-In is offered).
- Two viable toolchains either way: **Capacitor** (purpose-built for this, lighter) or **Flutter** via `webview_flutter` (heavier, but reuses existing Flutter tooling/CI/native-plugin experience from other projects — the only real argument for it here, since a full UI framework is otherwise overkill just to show a WebView).
- **Decision: not pursuing this for now.** Revisit if/when an actual App Store presence becomes worth the iOS native-functionality overhead.

## Pläne UX overhaul (real-device feedback pass)

After the first Pläne deploy, live feedback from actual phone use (Pixel 8, screenshot-driven) surfaced several real UX problems — fixed in one pass:

- **Unclear label**: "Durchgänge bis 6/6" → "Anläufe, bis alle 6 aus 1 m/1,5 m sitzen" (full sentence, no notation to decode).
- **Up & Down block had no distance context** — added "10–15 m vom Loch entfernt" to the description.
- **Inconsistent ball counts** (6/10/12 across blocks) — standardized Mitteldistanz and Lag-Putts from "von 10" to "von 12" (Richtwert also rescaled 7/10 → 8/12), leaving only two counts in the whole plan: 12 and the Kurze-Putts circle's 6.
- **Two real layout bugs found via screenshot, not guesswork**:
  1. `#plans-step-panes` (the wrapper `paneHtml()` renders into) wasn't a flex container, so each pane's `flex:1` had nothing to grow into — content sat at the top of the screen with a large dead zone below the button instead of being vertically centered. Fixed by making the wrapper `display:flex; flex-direction:column; flex:1; min-height:0`.
  2. The bare `[hidden]` attribute selector loses to any later same-specificity class rule that sets `display` (e.g. `.link-secondary { display:flex }`) — this is *why* putting.js's original steps needed explicit `#id[hidden]` overrides, and it silently broke the new nav's "Zurück" button (stayed visible on step 1) and the punch-grid/gap focus outline getting clipped. Fixed once, globally: `[hidden] { display: none !important; }` near the top of `styles.css`, so this class of bug can't recur per-element.
- **Font sizes bumped twice** (once modestly, then significantly further after a real-device screenshot showed how much headroom there actually was) — pane titles, descriptions, field labels/inputs, punch-grid dots, history table all sized up.
- **Nav restructured to a fixed footer bar**: Zurück/Weiter/Speichern moved out of each scrollable pane into one persistent bar (`#plans-nav-back`/`#plans-nav-next`, styled with the existing `.footer-bar`+`.step-nav` combo) so they're always reachable without scrolling, even on blocks with several fields.
- **Plan picker replaced**: the sheet-based chip picker (fine for N options) was overkill for exactly 2 plans — swapped for a 2-tab segmented control (`.seg-control`, already used elsewhere in the app), in both the record view and the Statistik → Pläne segment, kept in sync via a shared `data-key` convention.
- **"Grün heute" reworked**: was a persistent header field visible across all 7 steps regardless of relevance; moved into block 2 (Up & Down) — asked once, right after the Einfühlen warmup, not before you've touched a green. Input changed from free text to a 1–5 tap scale (5=schnell, matches the app's other quick-tap fields) with a toggle to a real Stimp-value input for anyone who has one — mutually exclusive, switching modes clears the other. Range's analogous "Wind/Platz" field got the same relocation (into Teildistanzen, block 2) for consistency, staying plain text.
- **Follow-up correction**: putting "Grün heute" in the Up & Down block (as above) still read as jumbled on an actual phone screen — the green-speed widget sat wedged between the drill's description and its punch grid, mixing a one-off assessment with the drill itself. Moved again, this time into block 1 (Einfühlen) instead — its own description already says "Kalibriert dich auf die heutige Grüngeschwindigkeit", so recording that assessment belongs there, not bolted onto the next drill. Up & Down block is now just the drill + punch grid again.

### Verification
Full click-through in Firefox devtools at a Pixel-8-width viewport (412px) after each fix: confirmed centering, fixed nav, seg-control switching (both instances), green-scale tap + Stimp toggle, and a real save → history round-trip showing the new "Grün" column ("4/5"). No console errors. Test run deleted via `DELETE /api/plan-runs/3` afterward. Re-verified the Einfühlen/Up&Down split after the follow-up correction.

## Real app-shell bug: `#app` could grow past the viewport

User caught this by screenshot, not me — I initially and wrongly reassured them the footer nav "can't scroll away" because it lives outside `#plans-step-panes`. It scrolled away anyway on the Kurze Putts step (two 6-button count pickers stacked — the first pane in this app ever tall enough to expose the issue).

Root cause: `#app { min-height: 100dvh; ...; overflow: hidden; }` — `min-height` is a floor, not a cap. When a view's content needed more height than the viewport, `#app` simply grew taller than the screen instead of being held at the viewport height, so the *whole page* scrolled (dragging the "fixed" footer with it) instead of the intended internal `flex:1 + min-height:0 + overflow-y:auto` regions doing the scrolling. `overflow:hidden` on `#app` didn't help because it only clips a box that has a real ceiling — with `min-height` there wasn't one to clip against.

Fix: `min-height: 100dvh` → `height: 100dvh` in `frontend/styles.css`. This is an app-wide correctness fix, not Pläne-specific — Putten/Range just never had content tall enough to trigger it before. Verified by shrinking the viewport to 412×760 and clicking a button in the Kurze Putts pane's second (off-screen) field group: the *pane* scrolled internally to reveal it, the footer nav stayed pinned throughout, no console errors.

Not yet committed/pushed — this pass is still local, pending user confirmation to ship.

## Pläne history: table → cards (horizontal scroll was the real problem)

User's live screenshot of the Statistik → Pläne → Range history showed the table scrolled sideways with the Datum column cut off — the `<table>` I built earlier (see "Pläne UX overhaul" above) has up to 8 data columns for the Range plan, which never fits a phone width. Table + horizontal scroll is a bad pattern on mobile regardless of column count tuning.

Replaced with one card per run (`.plan-history-card`): date + delete in a header row, then all fields in a wrapping flex row (`.plan-history-card__fields`) — each field is a small label/value pair, and text fields (Notiz, Fokus, Wind/Platz) get `--wide` to take the full row instead of being squeezed into a chip. Nothing scrolls horizontally, ever, because wrapping text needs no fixed column width. `flatFields()` now tags each column with `wide: f.type === "text"`; `planRow()` (table row) became `historyCard()` (card div). Deleted the now-dead `.plan-table*` CSS.
