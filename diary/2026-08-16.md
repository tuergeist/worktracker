# 2026-08-16

## Guided training plans ("Pläne" tab)

Added a fourth top-level feature to scratchlab: multi-block guided training plans (Kurzspiel, Range) that the user works through step by step and logs as one run, alongside the existing single-exercise Putten/Range flows.

Trigger: user shared `~/Downloads/trainingsbogen.html`, a standalone HTML/JS training-sheet widget with two fixed multi-block plans (localStorage-backed). Decision was to port the content/structure into scratchlab properly, not the HTML itself — went through plan mode first (`/Users/cb/.claude/plans/tender-petting-lighthouse.md`).

### Design decisions (confirmed with user)
- New 4th bottom tab "Pläne" (not folded into Putten/Range, not settings-only).
- Plan content (blocks, minutes, field labels/text) ported 1:1 from the source HTML.
- Verlauf (history) of saved runs lives as a 3rd segment in the existing Statistik tab, next to Putten/Range.
- Plan *definitions* (which blocks, which fields) are static frontend data (`PLAN_DEFS` in `plans.js`), not a DB-backed catalogue — there's no plan editor, just two fixed plans. Backend stores each run's field values as an opaque JSON blob it never inspects, so future tweaks to block content need no backend change.
- Visual design intentionally NOT ported from the source HTML (different fonts/palette) — new UI reuses scratchlab's existing CSS tokens/classes.

### Changes Made

**Backend:**
- `backend/db.py`: new `PlanRun` model (`plan_runs` table) — `user_id` FK, `plan_key` (`"kurzspiel"`|`"range"`), `data_json` (opaque), `note`, `played_at`. Mirrors `Session`'s shape but generic.
- `backend/models.py`: `PlanRunCreate`/`PlanRunUpdate` Pydantic bodies.
- `backend/app.py`: `POST/GET/PATCH/DELETE /api/plan-runs` (plus `_plan_run_dict` serializer), same pattern as the existing `sessions` routes — no new `/stats` endpoint, history is a plain list (per-plan fields too heterogeneous for a shared aggregate like `avg_ppb`).
- Migration `migrations/versions/0d2322e915a3_add_plan_runs_table.py`, autogenerated via `alembic revision --autogenerate` against a local `docker compose up db` + built `worktracker` image, then applied and verified with `alembic upgrade head`.

**Frontend:**
- New `frontend/js/plans.js`: `PLAN_DEFS` (both plans' full block/field content), a dynamic step-wizard (block count varies 6–7, unlike Putten's fixed 3 steps), a 12-ball punch grid for the Kurzspiel Up&Down block, a live-computed "Gap" field (Range Wechselblock, `i5 - i7`), and the Statistik-tab history table (plain `<table>`, not the single-metric `.history-row` layout — fields are too heterogeneous per plan) with date-edit and delete, mirroring `putting.js`'s `editSessionDate`.
- `frontend/index.html`: new `#view-plans` section, new bottom-tab button (`data-tab="plaene"`), new 3rd segment button + `#stats-pane-plaene` in the Statistik tab.
- `frontend/js/main.js`: `VIEWS.plaene`, `initPlans()` wired into boot, 3rd-segment handling in `setSegment`/`renderActiveSegment`.
- `frontend/styles.css`: new `.plan-*` rules reusing existing tokens (`--primary`, `--divider`, etc.) instead of the source HTML's own palette/fonts.

### Notes
- Found and fixed a real CSS cascade bug while testing: `.step-pane { display: flex }` (a class rule) beats a bare `[hidden]` attribute selector of equal specificity when the class rule comes later in the stylesheet — this is *why* `putting.js`'s original 3 steps needed explicit `#id[hidden] { display: none }` overrides instead of relying on the `hidden` attribute alone. My dynamically-built `.plan-pane`s hit the same issue; fixed with `.plan-pane[hidden] { display: none; }` (class+attribute selector outranks the bare class rule regardless of source order). Worth remembering for any future dynamically-generated step/tab UI in this app.
